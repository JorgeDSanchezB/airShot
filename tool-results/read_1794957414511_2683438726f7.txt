    41→## FASE 1 — Plan Estratégico (Frontend & Backend)
    42→
    43→### 1.1 Objetivo y alcance
    44→
    45→AirShot es una aplicación web **local y de usuario único** que convierte una historia escrita por el usuario en un video ensamblado. Cadena de valor:
    46→
    47→```
    48→historia (es) → mejora LLM → storyboard (escenas ~6 s, 4–15 s)
    49→            → prompts visuales (en) + referencias (personajes/escenarios, niveles)
    50→            → imágenes base (IA o subida) → clips de video (proveedor intercambiable)
    51→            → narración TTS (VoiceStudio | ElevenLabs) [+ QA de audio opcional Earshot]
    52→            → ensamblaje FFmpeg (+ música opcional) → video final
    53→```
    54→
    55→Alcance de la versión 1:
    56→
    57→- Incluido: todo el flujo anterior, biblioteca de referencias global/de proyecto con niveles, estilos visuales, configuración cifrada de proveedores, ensamblaje con música opcional, módulo opcional Earshot (desactivado por defecto).
    58→- Excluido (y documentado para no ambigüedad): subtítulos, multiusuario real, autenticación real, generación de guiones desde cero (la historia la escribe el usuario), exportación a plataformas externas, cola de trabajos distribuida, facturación.
    59→
    60→**Preparación para multi-tenant sin reescribir el núcleo** (requisito del enunciado): ver §1.10. La decisión es no implementar auth ahora, pero dejar `Depends(get_current_user)` como contrato único de identidad y repositorios que reciben el contexto de usuario, de modo que añadir JWT/OAuth + `tenant_id` sea aditivo (columna + filtro en repos), no estructural.
    61→
    62→### 1.2 Actores y casos de uso
    63→
    64→Actores:
    65→
    66→1. **Usuario básico** — pega su historia y ejecuta el flujo automático hasta el video final; interviene solo para revisar y confirmar.
    67→2. **Usuario avanzado** — edita storyboard (texto, prompt, duración 4–15 s), elige nivel de referencias, elige proveedor de video y TTS, activa Earshot, sube música, ajusta parámetros de ensamblaje.
    68→3. **Bibliotecario de referencias** (rol del mismo usuario) — crea personajes/escenarios con IA o subiéndolos, decide ámbito global o de proyecto, gestiona imágenes de referencia.
    69→
    70→Casos de uso (el manejo de errores de cada UC sigue la taxonomía canónica de F3 §3.1; aquí solo se listan los flujos principales y alternos clave):
    71→
    72→| UC | Nombre | Actor | Flujo principal | Flujo alterno relevante |
    73→|---|---|---|---|---|
    74→| UC-01 | Crear proyecto con historia | básico | `POST /projects` → proyecto `draft` con `originalStory` | título vacío/largo → 422 `VALIDATION_ERROR` |
    75→| UC-02 | Generar storyboard | básico | `POST /projects/{id}/storyboard` → LLM mejora historia + divide en escenas (default 6 s) + `promptEn` por escena | LLM produce JSON inválido → reintentos → 502 `LLM_INVALID_OUTPUT` |
    76→| UC-03 | Editar escena | avanzado | `PATCH /scenes/{id}` (texto, prompt, duración, fuente de narración) | duración fuera de rango → 422 (rango leído de `GET /config`, no fijo en frontend) |
    77→| UC-04 | Gestionar referencias | bibliotecario | CRUD `/references` + imágenes (subida o IA) + nivel + ámbito | atributo no permitido/sensible → 422 (`SENSITIVE_KEY` / `ATTRIBUTE_LIMIT`) |
    78→| UC-05 | Asignar referencias a escena | avanzado | `PUT /scenes/{id}/references` (subject/environment) | excede tope por escena → 422 (tope desde `config.yaml`) |

    81→| UC-08 | Generar narración | básico | `POST /scenes/{id}/generate-audio` (VoiceStudio default) | VoiceStudio caído → 503 `PROVIDER_UNAVAILABLE` con indicación de cambiar a ElevenLabs |

    85→| UC-12 | Música opcional | avanzado | subir pista + volumen en assemble | formato no permitido → 415 |
    86→| UC-13 | Biblioteca de estilos | avanzado | CRUD `/visual-styles`; estilos seed no eliminables | borrar seed → 409 `DELETION_FORBIDDEN` |
    87→| UC-14 | Flujo automático completo | básico | orquestación cliente de UC-02 → UC-06/07/08 por escena → UC-09 | pausa/reanuda por escena; sin ejecución silenciosa en segundo plano |

   106→### 1.4 Riesgos y mitigaciones
   107→
   108→| ID | Riesgo | Impacto | Mitigación diseñada |
   109→|---|---|---|---|
   110→| R-01 | Costo variable de APIs externas (lo asume el usuario) | financiero | Antes de cada generación por lote, la UI muestra resumen (n.º escenas × duración efectiva por proveedor). No hay cobro desde AirShot |
   111→| R-02 | Duraciones soportadas distintas por proveedor | funcional | `DurationMapper` por proveedor (ADR-009) con redondeo documentado y advertencia en UI cuando la duración efectiva ≠ solicitada |
   112→| R-03 | Límite de imágenes de referencia por proveedor (Veo hasta 3; otros varían) | funcional | `reference_image_limit` por proveedor en `providers.yaml` + política por nivel (§2.6) + selección de imágenes primarias en el payload |
   113→| R-04 | Términos de servicio / licencias de contenido de proveedores | legal | Documentado: la responsabilidad del contenido y del uso de las APIs es del usuario; AirShot no distribuye contenido. No se da asesoría legal |
   114→| R-05 | VoiceStudio no disponible (local caído) | disponibilidad | Health check profundo + error 503 con remediación explícita («cambia a ElevenLabs o levanta VoiceStudio»); nunca fallback silencioso |
   115→| R-06 | FFmpeg ausente o de versión distinta | bloqueo ensamblaje | Health check + instalación declarada en Docker/Makefile; `AssemblyService` encapsula para sustituir por alternativa (ADR-011) |
   116→| R-07 | LLM devuelve JSON malformado o escenas fuera de límites | flujo | Validación Pydantic del output + `llm.max_retries` + 502 `LLM_INVALID_OUTPUT` con detalle |
   117→| R-08 | Historias muy largas → storyboards enormes | memoria/tiempo | `scene.max_scenes_per_project` configurable; división por lotes en `StoryboardService`; paginación por cursor en listas |
   118→| R-09 | Pérdida de API keys | seguridad | Cifrado Fernet en reposo (ADR-012), enmascarado en respuestas, nunca en logs |
   119→| R-10 | Deprecación/cambio de API de un proveedor | mantenimiento | Aislamiento en adaptadores (ADR-002/007); el resto del sistema no conoce endpoints |
   120→| R-11 | Earshot no disponible o con contrato inestable | QA de audio (módulo opcional) bloqueado | Health check profundo + 503 `PROVIDER_UNAVAILABLE` con remediación; el pipeline principal no depende de Earshot (ADR-013) |

   122→### 1.5 Arquitectura general
   123→
   124→Modelo: **arquitectura en capas simplificada con puertos y adaptadores solo donde hay variabilidad real** (ADR-002). No microservicios, no CQRS, no event sourcing, no GraphQL (todas descartadas en §1.9 con motivo).
   125→
   126→```
   127→┌──────────────────────────────────────────────────────────────────────────────┐
   128→│ PRESENTACIÓN                                                                  │
   129→│  Backend: FastAPI routers (presentation/api)   Frontend: React+Vite SPA       │
   130→└───────────────┬──────────────────────────────────────┬───────────────────────┘
   131→                │ use cases (application)               │ TanStack Query + Zustand
   132→┌───────────────▼──────────────────────────────────────────────────────────────┐
   133→│ APLICACIÓN — casos de uso orquestando dominio e infraestructura                │
   134→│  CreateProject, GenerateStoryboard, GenerateSceneImage, GenerateSceneVideo,    │
   135→│  GenerateSceneAudio, AssembleProject, RunAudioQA, CRUD de referencias/estilos │
   136→└───────────────┬──────────────────────────────────────────────────────────────┘
   137→                │
   138→┌───────────────▼──────────────────────────────────────────────────────────────┐
   139→│ DOMINIO — entidades (Project, Scene, Reference, VisualStyle, ProviderConfig,  │
   140→│  AssemblyJob, SceneReference), servicios puros (PromptComposer,               │
   141→│  DurationMapper, ReferenceValidator), puertos (interfaces) y enums            │
   142→└───────┬──────────────────────────┬─────────────────────────┬─────────────────┘
   143→        │                          │                         │
   144→┌───────▼────────┐        ┌────────▼─────────────┐   ┌──────▼──────────────────┐
   145→│ PERSISTENCIA   │        │ PROVEEDORES EXTERNOS  │   │ MEDIOS DE EJECUCIÓN      │
   146→│ SQLAlchemy 2.0 │        │ ports → adapters:     │   │ StorageService (FS local │
   147→│ async + repos  │        │ Video(TTS/LLM/Image/  │   │ ./data), AssemblyService │
   148→│ (SQLite→PG)    │        │ AudioQA) providers    │   │ (FFmpeg subprocess)      │
   149→└────────────────┘        └───────────────────────┘   └─────────────────────────┘
   150→```
   151→
   152→**Por qué este modelo y no otro** (problema → coste → alternativa descartada):
   153→
   154→- Problema que resuelve: (a) los proveedores externos son intercambiables por requisito (Veo/Kling/Runway/Luma; VoiceStudio/ElevenLabs; LLM; image-gen; Earshot); (b) SQLite→PostgreSQL y FS local→S3 son migraciones previstas; (c) FFmpeg puede sustituirse.
   155→- Coste que introduce: indirección (puertos + repositorios + inyección en el composition root). Aceptado porque la variabilidad es real y está en el enunciado.
   156→- Alternativa descartada: (1) hexagonal estricto con capa anti-corrupción por cada proveedor — sobreingeniería para un single-user local (no hay traducción de modelos de dominio externos que justifique ACL formal); (2) arquitectura «big ball of mud» con SDKs importados en los use cases — acopla el núcleo a endpoints concretos y viola la regla del enunciado de intercambiabilidad; (3) microservicios — no hay necesidad de escalado independiente ni de despliegue distribuido (coste operativo alto, beneficio nulo en local).
   157→
   158→Módulos concretos (árbol completo en Fase 6 §6.2):
   159→
   160→- `app/core`: `config.py` (Pydantic Settings sobre `config.yaml` + env), `errors.py` (taxonomía + RFC 7807), `logging.py`.
   161→- `app/domain`: `entities/`, `ports/`, `services/` (puros, sin I/O), `enums.py`.
   162→- `app/application`: casos de uso por operación de negocio.
   163→- `app/infrastructure`: `persistence/` (SQLAlchemy + repos), `providers/` (adaptadores + `registry.py` + `providers.yaml`), `storage/`, `assembly/`.
   164→- `app/presentation`: routers FastAPI, schemas Pydantic de request/response, dependencies.
   165→
   166→Frontend (organización Átomos → Moléculas → Organismos → Páginas):
   167→
   168→- **Átomos** (shadcn/ui + wrappers finos): `Button`, `Badge`, `DurationSlider`, `StatusChip`, `TextField`, `ConfirmDialog`.
   169→- **Moléculas**: `SceneCard`, `ReferenceCard`, `ReferenceForm`, `AudioPanel`, `GenerateVideoDialog`, `PromptEditor`, `AssetPreview`, `VoicePicker`, `LevelSelector`, `AttributeRows` (render dinámico de §5.4), `ErrorNotice` (problema RFC 7807 → mensaje accionable).
   170→- **Organismos**: `StoryboardList` (virtualizado), `ReferenceLibrary` (virtualizado), `ProviderSettingsForm`, `AssemblyPanel`, `AudioQAPanel`, `MusicPicker`, `StylePicker`, `ProjectForm`.

   173→### 1.6 Gestión de estado (justificación detallada)
   174→
   175→- **Estado de servidor** (proyectos, escenas, referencias, estilos, configs, jobs): TanStack Query. Problema que resuelve: caché, reintentos, listas infinitas con cursor (`useInfiniteQuery`), invalidación tras mutaciones, evita condiciones de carrera de `useEffect`+fetch manual. Coste: convención de claves y boilerplate de invalidación. Alternativa descartada: `useEffect` + estado local (condiciones de carrera y stale reads), Redux RTK Query (boilerplate mayor sin beneficio aquí), SWR (soporte de listas infinitas con cursor menos directo en escenarios de invalidación encadenada).
   176→- **Estado de cliente** (pestaña activa, escena seleccionada, borradores del editor de prompt, ajustes de vista): Zustand. Problema: estado UI efímero compartido entre organismos sin prop drilling. Coste: disciplina de no duplicar estado de servidor. Alternativa descartada: Redux Toolkit (boilerplate de actions/reducers para una app single-user local), Context API (re-renders en cascada que dañan listas virtualizadas).
   177→- **Regla de propiedad**: cada dato vive en exactamente un lugar. Nada que venga del API se guarda en Zustand; nada puramente UI se mete en TanStack Query.

   179→### 1.7 Decisiones tecnológicas (resumen; detalle en ADRs)
   180→
   181→| Decisión | ADR | Resumen de justificación | Alternativa descartada |
   182→|---|---|---|---|
   183→| FastAPI + Pydantic v2 | ADR-010 (contexto) | Async nativo para llamadas a proveedores lentos, validación declarativa, OpenAPI automática | Django (ORM monolítico y peso innecesario), Flask (sin validación ni async nativos) |
   184→| SQLite + SQLAlchemy 2.0 async + repositorios | ADR-001 | Local, portable, sin servidor; repos abstraen para migrar a PG | PostgreSQL en local (servidor innecesario v1), SQLModel (menos maduro para el mix async/JSONB usado) |
   185→| Alembic para migraciones | ADR-001 | Historial versionado del esquema; ruta SQLite→PG | `create_all` (sin historial ni retrocompatibilidad) |
   186→| Atributos dinámicos en JSONB (TEXT JSON en SQLite) + JSON Schema | ADR-003 | Extensibilidad sin migraciones (regla del enunciado) | EAV (consultable pero complejo; no hay requisito de filtrar por atributo), columnas fijas (rígido) |
   187→| UUID v4 como identidad | ADR-004 | Claves estables en frontend y en reordenaciones (LISTÓN exige «nunca el índice») | INTEGER autoincrement (inestable para keys de React en listas editables) |
   188→| Paginación por cursor (createdAt+id; order_index en escenas) | ADR-005 | Escalable con n grande; sin saltos ni duplicados bajo inserciones | OFFSET (degradación O(n) y duplicados con datos cambiantes) |
   189→| Taxonomía de 7 tipos de error + RFC 7807 | ADR-006 | Distingue ausente/nulo/inválido/temporal/auth/config/crítico y no oculta | Excepciones genéricas con mensaje plano; códigos ad hoc inconsistentes |
   190→| Strategy + Factory con registro `providers.yaml` | ADR-007 | Añadir proveedor = nuevo adaptador + entrada de registro, sin tocar núcleo | if/else por proveedor (vierte detalles de cada API en el núcleo) |
   191→| React 18 + TS + Vite SPA | ADR-008 | Herramienta local de una página; sin SSR no se justifica Next | Next.js (SSR/RSC innecesarios para un cliente local contra API propia) |
   192→| shadcn/ui (Radix + Tailwind) | ADR-008 | Accesibilidad incluida, consistencia visual | Librería de componentes con runtime pesado o CSS desde cero |
   193→| Zustand + TanStack Query + @tanstack/react-virtual | ADR-008 | §1.6 + virtualización del LISTÓN | Redux Toolkit / Apollo / renderizado completo de listas |
   194→| `DurationMapper` por proveedor | ADR-009 | Mapea 4–15 s del usuario a duraciones soportadas | Rechazar duraciones no exactas (rompe el flujo) |
   195→| Extensión de `providerType` a `video|tts|llm|image|audio_qa` | ADR-010 | El enunciado exige LLM (mejora+prompts), imágenes base por IA y Earshot; su modelo solo tipaba `video|tts` | Quedarse en dos tipos (obligaría a mezclar LLM/image en tablas ajenas) |
   196→| FFmpeg vía subprocess encapsulado en `AssemblyService` | ADR-011 | Control total de argumentos, sin shell, timeout configurable; sustituible | MoviePy (abstracción con coste de depuración mayor y dependencia pesada), Celery/cola distribuida (innecesario) |
   197→| Cifrado Fernet de API keys + secretos por env | ADR-012 | Reposo cifrado; nunca en config versionado | Claves en `config.yaml` (fugas por VCS), claves en claro (inaceptable) |

   199→| Sincronismo por operación: storyboard/imágenes/audio sync; video/assembly/audio-qa async | ADR-014 | Latencias: LLM/image/TTS segundos; video/ffmpeg minutos → 202 + sondeo | Todo síncrono (timeouts HTTP), todo job-queue (sobreingeniería v1) |
   200→| Idioma de los prompts: inglés (historia y UI en español) | ADR-015 | Rendimiento cualitativo de modelos de imagen/video (supuesto A-03); INV-13 lo refuerza | Prompts en español (degradación esperada de calidad) |

   202→### 1.8 Anti-sobreingeniería: patrones usados y patrones descartados
   203→
   204→Tabla de patrones usados (problema → coste → alternativa descartada). El resto de patrones del mercado se declara **descartado** con motivo:
   205→
   206→| Patrón usado | Problema que resuelve | Coste introducido | Alternativa descartada |
   207→|---|---|---|---|
   208→| Capas + puertos (variabilidad real) | Intercambio de proveedores/DB/storage | Indirección | Núcleo acoplado a SDKs concretos |
   209→| Repository | Migración SQLite→PG sin tocar dominio | Boilerplate | Consultas dispersas en use cases |
   210→| Strategy + Factory (proveedores) | N proveedores con misma interfaz | Registro + config | if/else en use cases |
   211→| DTO Pydantic (request/response) | Validación de contrato y OpenAPI | Duplicación entidad/DTO | Entidades expuestas directo (acoplamiento HTTP↔persistencia) |
   212→| Cursor pagination | Listas escalables estables | Codificación opaca de cursor | OFFSET/LIMIT |
   213→| JSONB + JSON Schema | Atributos dinámicos | Validación imperativa de profundidad | EAV / columnas fijas |
   214→| Virtualización (@tanstack/react-virtual) | DOM acotado con miles de escenas | Estimación de alturas y medición | Renderizar todo |
   215→| React.memo + comparador | Evitar re-render de 200 tarjetas al parchear una | Mantener comparador | Re-render completo |
   216→
   217→**Descartados explícitamente** (porque no hay requisito que los justifique y su costo sí existe): microservicios, event sourcing, CQRS, GraphQL, message broker/cola distribuida, OAuth server propio, k8s, i18n multi-idioma (UI solo español, supuesto A-03), caché Redis (la memoria local del cliente TanStack Query basta), autenticación multiusuario real en v1 (queda el hueco §1.10), websockets (el sondeo corto es suficiente en single-user; se reevalúa en v2 si se añade multiusuario).
   218→
   219→### 1.9 Cero hardcoding: estrategia de configuración
   220→
   221→- Fuente única: `config.yaml` (Anexo A, completo) validado en arranque por Pydantic Settings (`app/core/config.py`); override por variables de entorno para secretos (`AIRSHOT_SECRET_KEY`). Todo límite del sistema referenciado en este documento tiene clave de config: duraciones de escena (§2.3), límites de atributos (§4.2), tamaños de subida (§3.2), paginación (§3.1), timeouts/reintentos/concurrencia por proveedor (Anexo B), parámetros de ensamblaje (§3.2), longitudes de texto de entidades (§2.3: `story.*`, `reference.*`, `visual_style.*`), imágenes de referencia por nivel (§2.6: `reference.level_image_limits`) y caché de media (§3.5: `media.*`).
   222→- `GET /api/v1/config` expone en runtime los límites efectivos de solo lectura para que el frontend NO duplique constantes de negocio (el slider de duración toma min/default/max de ahí, no de un literal).
   223→- Constantes técnicas permitidas y justificadas (no son negocio): versión del esquema de atributos `v1`; `UUID` versión 4; encoding JSON UTF-8; base de rutas `/api/v1`; los umbrales de virtualización del frontend (`threshold: 50`, alturas estimadas) por ser constantes de rendimiento de UI documentadas en `src/config/app.config.ts` con justificación (§5.3); nombre del usuario local por defecto (`local-user`, de `config.yaml app.local_user_id`); el rango físico `(0, 1]` de `musicVolume` (fracción de mezcla, no límite de negocio).
   224→- Los límites del negocio **no** se duplican como CHECKs SQL con literales (§2.4 explica por qué: mantenerlos configurables); solo invariantes estructurales van a la BD.
   225→
   226→### 1.10 Preparación multi-tenant (sin implementar ahora)
   227→
   228→1. `Depends(get_current_user)` es el único punto de identidad; hoy devuelve `LocalUser` fijo (de config). JWT/OAuth futuro = mismo contrato, otra implementación (sin tocar controllers).
   229→2. Los repositorios reciben el contexto de usuario en su constructor por sesión; añadir `tenant_id` será: columna nullable + filtro en repos (ADR-001) — cambio aditivo, el dominio no conoce tenancy.
   230→3. `StorageService` ya direcciona por `projectId` (rutas `outputs/projects/{projectId}/...`), por lo que el aislamiento de ficheros ya es por proyecto y admite prefijo de tenant futuro.
   231→4. Límite honesto: no hay aislamiento real hoy porque no hay autenticación; esta sección declara el camino, no un estado.

   235→## FASE 2 — Modelado de Datos (Base Sólida)
   236→
   237→### 2.1 Entidad base
   238→
   239→`IEntity` (interfaz de dominio): `id: UUID` y `createdAt: datetime` (UTC, ISO 8601). Implementación en SQLite: `id` como `TEXT(36)` con valor `uuid4` generado por el dominio (no por la BD); `createdAt` como `DateTime` con timezone serializado ISO en SQLite. Las FKs con `ON DELETE` solo se aplican si el engine activa `PRAGMA foreign_keys=ON` por conexión (event listener del engine — ADR-001).
   240→
   241→Justificación del UUID v4 (ADR-004). Problema: el LISTÓN exige claves estables en frontend («nunca el índice») y las listas son editables (reordenar/borrar inserta huecos en índices autoincrementales). Coste: índices con insert order aleatorio (fragmentación); aceptable en SQLite local con decenas de miles de filas. Alternativa descartada: `INTEGER PRIMARY KEY` autoincrement (claves de React inestables en listas editables; además impide fusionar datos multi-tenant futuros sin colisiones).
   242→
   243→### 2.2 Diagrama entidad-relación
   244→
   245→```
   246→Project 1 ──── n Scene
   247→Project 1 ──── n AssemblyJob
   248→Project 1 ──── 0..1 musicAsset (storage key)
   249→Scene   n ──── n Reference        (a través de SceneReference, kind: subject|environment)
   250→Project * ── 0..1 VisualStyle   (un proyecto referencia 0..1 estilo; un estilo puede usarse en muchos proyectos; FK nullable visual_style_id)
   251→Reference: project_id nullable  ⇔  library_scope ∈ {global, project}
   252→ProviderConfig: sin FK (proveedores independientes de proyectos; el proyecto guarda el *nombre* del proveedor activo)
   253→```
   254→
   255→El modelo relacional completo (columnas, tipos, nulidad) se declara en SQLAlchemy 2.0 `Mapped`/`mapped_column` con tipos dialecto-conscientes: `JSONVariant` = `sa.JSON().with_variant(postgresql.JSONB, "postgresql")` para que la misma definición de columnas sea JSONB nativa en PostgreSQL y TEXT-JSON en SQLite (ruta de migración ADR-001/ADR-003).
   256→

   383→### 2.4 Invariantes, validaciones y dónde se aplican
   384→
   385→Tabla canónica (INV). Principio declarado: **los invariantes estructurales van a la BD (CHECKs); los límites de negocio NO (viven en config y se validan en API/servicio), para que cambiar un límite no requiera migración de esquema** (cero hardcoding, LISTÓN punto 6). Cada fila declara capa de aplicación.
   386→
   387→| INV | Invariante | Capa |
   388→|---|---|---|
   389→| INV-01 | `Scene.projectId` existe; borrar proyecto borra sus escenas | BD (FK CASCADE) |
   390→| INV-02 | `Scene.orderIndex` único por proyecto y ≥ 0; contigüidad 0..n-1 tras cada operación de orden | BD (índice único compuesto) + servicio (contigüidad) |
   391→| INV-03 | `durationSeconds` ∈ [min, max] de config | API (Pydantic, lee config) — no CHECK SQL (deliberado, ver principio) |
   392→| INV-04 | `Reference`: `libraryScope="global"` ⇔ `projectId IS NULL` | BD (CHECK compuesto; invariante estructural, no límite) |
   393→| INV-05 | `referenceImages`: ≤ max de config; ids únicos; 1 primaria si no vacío | Servicio/validador (config) |
   394→| INV-06 | `attributes`: valida contra JSON Schema v1 + límites de config | `ReferenceValidator` (F4) |
   395→| INV-07 | `ProviderConfig (providerType, providerName)` único; `providerName` ∈ registro `providers.yaml` | BD (único compuesto) + validación contra registro |
   396→| INV-08 | `Scene.status` solo transiciones válidas (§2.3) | Use case (máquina de estados en dominio) |
   397→| INV-09 | Ensamblaje solo si todas las escenas tienen video y (audio o `assembly.require_audio=false`) | Use case (409 si no) |
   398→| INV-10 | `SceneReference` única por (sceneId, referenceId); conteos por kind ≤ config | BD (único) + API (conteos) |
   399→| INV-11 | `VisualStyle.name` único; `isCustom=false` no borrable | BD + use case |
   400→| INV-12 | `AssemblyJob` con `jobType=assembly` solo `completed` si `outputPath` no nulo | Use case |
   401→| INV-13 | `Scene.promptEn` solo con caracteres ASCII imprimibles + puntuación común (los prompts son en inglés; el storyboard lo garantiza; PATCH lo valida) | API (Pydantic) |
   402→| INV-14 | `ProviderConfig.apiKeyEncrypted` nunca se devuelve en respuestas (solo `apiKeyMasked`) | Presentación |
   403→
   404→Nota SQLite: las FKs y CHECKs solo se aplican si el engine activa `PRAGMA foreign_keys=ON` por conexión (event listener — §2.1, ADR-001); INV-01/INV-04 tienen test de contrato previsto en §6.6.
   405→
   406→### 2.5 Atributos dinámicos: JSONB vs alternativas
   407→
   408→Decisión (ADR-003): `attributes` y `referenceImages` como JSONB (`sa.JSON` con variante `JSONB` para PostgreSQL). En SQLite se serializan como TEXT con validación de JSON + JSON Schema en la capa de aplicación en cada escritura.
   409→
   410→| Criterio | JSONB | EAV | Columnas fijas |
   411→|---|---|---|---|
   412→| Añadir atributo (hairColor) | sin cambio de esquema ni de núcleo | sin cambio de esquema (filas nuevas) | requiere ALTER TABLE |
   413→| Consultar/filtrar por atributo | soportado (SQLite: LIKE/`json_extract`; PG: operadores nativos) | soportado (JOIN) | nativo |
   414→| Complejidad de código | baja (dict + schema) | alta (N filas, N+1 en lectura, reconstruction de objeto) | baja |
   415→| Integridad | JSON Schema en escritura | tipos por fila, dispersa | CHECKs por columna |
   416→| Coste real en AirShot | lectura entera por referencia (referencias son decenas-cientos) | sobre-coste estructural sin requisito de filtro por atributo (v1 no filtra por atributo: ver §3.2) | viola regla del enunciado |
   417→
   418→Alternativa descartada EAV: no existe requisito de consultar por atributo (los listados filtran por nombre/tipo/level/scope, todos columnas). Alternativa descartada columnas fijas: el enunciado exige añadir atributos sin migración. Coste aceptado de JSONB: validación imperativa de profundidad y tamaño (F4 §4.2), sin índices sobre atributos en v1.
   419→
   420→### 2.6 Factories (solo las que aportan valor; el resto descartado)
   421→
   422→- `ReferenceFactory` (dominio): construye `Reference` garantizando invariantes INV-04/05/06 en un solo lugar: normaliza `libraryScope`↔`projectId`, sella `attributesSchemaVersion`, fija la primera imagen como primaria, aplica defaults de `level`. Problema: dispersión de invariantes en controllers. Coste: una clase más. Alternativa descartada: constructores directos dispersos (invariantes repartidas y divergentes).
   423→- `VideoProviderFactory`, `TTSProviderFactory`, `LLMProviderFactory`, `ImageProviderFactory`, `AudioQAProviderFactory` (infraestructura, uno por tipo de puerto): instancian adaptadores desde `providers.yaml` (registro declarativo) + `ProviderConfig` (secretos/baseUrl/params). Problema: intercambiabilidad LISTÓN. Coste: registro + resolución de nombres. Alternativa descartada: if/else por proveedor en use cases (acopla núcleo; el ejemplo del ProviderX en §4.8 fallaría).
   424→- **Descartados**: Builder (ningún objeto requiere construcción paso a paso paramétrica — la creación es de una vez con validación), Abstract Factory adicional (no hay familias de objetos relacionadas), Prototype (no hay costo de creación relevante).
   425→
   426→**Política de uso por `level`** (hogar único de la regla; la citan §2.3 y R-03; la ejecutan `PromptComposer` y la selección de imágenes en el use case de video):
   427→
   428→| `level` | Qué entra al `promptEn` | Imágenes de referencia usadas |
   429→|---|---|---|
   430→| `basic` | `name` + `description` | hasta `reference.level_image_limits.basic` (1) — la primaria |
   431→| `advanced` | lo anterior + todos los `attributes` | hasta `reference.level_image_limits.advanced` (2) |
   432→| `cinematic` | lo anterior + fragmento de cohesión con el `VisualStyle` del proyecto | hasta el `reference_image_limit` del proveedor (`level_image_limits.cinematic = null` = sin tope de nivel) |
   433→
   434→El tope efectivo por generación es `min(level_image_limits[level] (si no es null), reference_image_limit del proveedor)`; el total de imágenes por referencia nunca excede `reference.max_images_per_reference`.

   463→
   464→### 3.1 Convenciones generales (transversales)
   465→
   466→Base de rutas: `/api/v1` (prefijo versionado; constantes técnicas justificadas). JSON UTF-8. Errores siempre RFC 7807 (Problem Details) con extensiones propias: `code`, `traceId`, `retryable`, y contexto opcional (`provider`, `sceneId`, `field`, `hints[]` — sugerencias accionables para la UI).
   467→
   468→#### 3.1.1 Taxonomía canónica de tolerancia a fallos (LISTÓN punto 5; referencia única para todo el documento)
   469→
   470→| Tipo | Definición | Tratamiento API | HTTP | `code` | ¿Reintentar? |
   471→|---|---|---|---|---|---|
   472→| **Campo opcional ausente** | La clave no viene en el payload | PATCH/POST aplican el valor previo/default declarado del campo; el comportamiento se documenta por endpoint (no es error) | — (200/201/202) | — | — |
   473→| **Valor nulo** | La clave viene con `null` y el campo es nullable | Se asigna null con la semántica documentada en §2.3 (p. ej. `improvedStory: null` = «sin storyboard») | 200 | — | — |
   474→| **Valor nulo en campo no nullable** | La clave viene con `null` y el campo no lo permite | Rechazo explícito (nunca coercion a vacío/default) | 422 | `VALIDATION_ERROR` | no |
   475→| **Dato inválido** | Tipo/formato/rango incorrecto (duración fuera de [min,max], UUID malformado, `limit=0`, enum desconocido) | Rechazo con detalle de campo; los rangos se leen de config, no hardcodeados | 422 | `VALIDATION_ERROR` / `UNEXPECTED_FIELD` (campo desconocido: se rechaza, no se descarta en silencio) | no |
   476→| **Error temporal** | Timeout/remoto 5xx/429/conexión del proveedor | Reintentos con backoff exponencial (`max_retries`, `backoff_base_seconds` por proveedor); agotados → problema con `retryable=true`; asset/estado marcado fallido-reintentable | 504 (timeout) / 503 (unavailable/rate) | `PROVIDER_TIMEOUT` / `PROVIDER_UNAVAILABLE` / `PROVIDER_RATE_LIMIT` | sí (UI ofrece botón reintentar) |
   477→| **Error de autorización (proveedor)** | 401/403 del proveedor (API key inválida) | Sin reintentos (no es transitorio); se marca `ProviderConfig.lastCheck`; mensaje apunta a Configuración; **nunca fallback a otro proveedor en silencio** | 502 | `PROVIDER_AUTH` | no (corregir key) |
   478→| **Error de configuración** | Proveedor elegido sin `ProviderConfig`, nombre no registrado, o key ausente | Fail fast ANTES de llamar al proveedor | 409 | `PROVIDER_NOT_CONFIGURED` | no (configurar) |
   479→| **Fallo crítico** | Excepción no controlada (bug), BD corrompida | 500, log con traceId, job/estado `failed` con snapshot del problema; sin ocultamiento | 500 | `INTERNAL_ERROR` | no |
   480→| No encontrado | Recurso inexistente | — | 404 | `NOT_FOUND` | no |
   481→| Estado inválido | Operación contra estado incorrecto (ensamblar con escenas incompletas, borrar seed, regenerate sin storyboard) | — | 409 | `ASSEMBLY_INCOMPLETE_SCENES` / `DELETION_FORBIDDEN` / `STATE_CONFLICT` | tras corregir estado |
   482→| Payload excesivo | Body > `app.max_body_bytes` | — | 413 | `PAYLOAD_TOO_LARGE` | no |
   483→| Medio no soportado | Upload con mimetype fuera de whitelist | — | 415 | `UNSUPPORTED_MEDIA` | no |
   484→| Salida inválida del LLM | JSON estructuralmente inválido agotados los reintentos (UC-02) | sin reintentos adicionales; el usuario ajusta y regenera | 502 | `LLM_INVALID_OUTPUT` | no |
   485→| Límite de imágenes de referencia | superado `reference.max_images_per_reference` | — | 422 | `REFERENCE_IMAGE_LIMIT` | no |
   486→| Validación de atributos (F4 §4.2) | familia `ATTRIBUTE_*` y `SENSITIVE_KEY`, un `code` por control C-01..C-13 | — | 422 | ver §4.2 | no |
   487→
   488→Reglas adicionales de honestidad: ningún catch vacío; ningún `except: pass`; los errores de proveedor se registran con su `code` original en `detail` (preservando causa); los valores por defecto solo se aplican en el caso «ausente» y siempre están documentados en §2.3.
   489→
   490→#### 3.1.2 Autenticación (hueco preparado)
   491→
   492→Todos los routers dependen de `Depends(get_current_user)`. Hoy: devuelve `LocalUser(id=config.app.local_user_id)` — usuario local único (supuesto A-07). Mañana: la misma dependency resuelve JWT/OAuth; ningún controller cambia. No hay autorización por recurso en v1 (single-user); la UI no muestra login.
   493→
   494→#### 3.1.3 Paginación por cursor (LISTÓN punto «Lista Infinita»)
   495→
   496→- **Todos** los listados sin excepción (proyectos, escenas por proyecto, referencias, estilos, provider-configs, assemblies por proyecto, voces TTS) aceptan `?limit=&cursor=`.
   497→- `limit`: entero ≥ 1; default `pagination.default_page_size` (25); máximo `pagination.max_page_size` (100); `limit > max` → 422 `VALIDATION_ERROR` con hint del máximo (no se recorta en silencio).
   498→- `cursor`: opaco (base64url de la clave de ordenación compuesta). Envolvente de respuesta:
   499→
   500→```json
   501→{ "items": [ /* ≤ limit; default 25, máx pagination.max_page_size */ ], "nextCursor": "b64…|null", "limit": 25 }
   502→```
   503→
   504→- `nextCursor == null` ⇒ no hay más páginas. No se devuelve `total` (COUNT(*) es O(n) en toda la tabla y rompe la escalabilidad; alternativa descartada y documentada — la UI usa «cargar más» infinito).
   505→- Claves de ordenación por endpoint (siempre deterministas: clave de negocio + desempate por `id`):
   506→  - Colecciones por `createdAt`: cursor = `(createdAt, id)`; predicado SQL expandido portable: `(created_at < :c) OR (created_at = :c AND id < :i)` con `ORDER BY created_at DESC, id DESC` (o ASC). El desempate por `id` evita duplicados/pérdidas con timestamps empatados.
   507→  - Escenas dentro de proyecto por defecto `sortBy=order`: cursor = `orderIndex` (único dentro del proyecto gracias a INV-02; sin desempate necesario); `sortBy=createdAt` también permitido (cursor `(createdAt,id)`).
   508→- `sortBy` y `order` son whitelists por endpoint (`order: asc|desc`); valores fuera de whitelist → 422 `VALIDATION_ERROR`. Sorts arbitrarios (por `title`, etc.) quedan fuera del contrato v1 porque rompen la estabilidad del cursor; se declara como extensión futura con su propia clave compuesta.
   509→- Filtros combinables con cursor (`?status=&type=&level=&scope=&q=`): los predicados se encadenan al de cursor. Los filtros de rango (`status`, `type`, `level`, `scope`, `projectId`) tienen índice dedicado (§2.7); `q` (prefijo `name LIKE q%`), `origin`, `jobType` y `status` en proyectos son **predicados residuales** aceptados deliberadamente a escala local (página recuperada por el índice de orden + filtrado en memoria de la página) — declaración explícita, no omisión.
   510→- Cursor malformado, ilegible o inconsistente con el `sortBy` de la request → 422 `VALIDATION_ERROR` (dato inválido; nunca se ignora en silencio).
   511→- Complejidad real declarada: cada página es O(limit) filas vía seek de índice (sin OFFSET); memoria O(limit) en servidor; el estado de paginación vive en el cliente (cursor), no en sesión de servidor. Límites prácticos declarados: (a) tamaño de página ≤ 100 y payloads de escena con textos largos → hasta pocos MB por página (por eso `max_page_size` es configurable y conservador); (b) SQLite maneja millones de filas con estos índices, pero el cuello real es el payload HTTP, no la BD; (c) inserciones concurrentes durante la paginación no producen duplicados (cursor por clave estable).
   512→
   513→#### 3.1.4 Concurrencia y rate limiting por proveedor
   514→
   515→- Cada proveedor del registro `providers.yaml` define `max_concurrent` (semáforo asyncio por proveedor, p. ej. Veo 2, Kling 1). Cola de espera sin límite en v1 (single-user; se declara límite práctico: la UI no permite lanzar más de N escenas en lote — N configurable vía `app.batch_max_operations`).
   516→- HTTP 429 propio (rate limit de AirShot) queda **reservado y no implementado** en v1 (no existe multiusuario); se declara explícitamente para no fingir capacidad.
   517→- Timeouts y reintentos por operación son los del Anexo B por proveedor (`timeout_seconds`, `max_retries`, `backoff_base_seconds`).
   518→- **Regla de resolución de proveedor** para una operación: `providerOverride` del request > campo del proyecto (`videoProvider` / `ttsProvider`) > default de `config.yaml` (`providers.default_tts`, `providers.default_llm`, `providers.default_image`). El proveedor resuelto sin `ProviderConfig` activo con key → 409 `PROVIDER_NOT_CONFIGURED` (fail fast).

   804→### 3.4 Contrato asíncrono y sondeo
   805→
   806→- `generate-video`, `assemble` y `audio-qa` devuelven 202 y exponen su estado vía recurso sondeable (escena o job). Transiciones: escena `video_pending → video_ready | failed`; job `pending → running → completed | failed`. Los errores de proveedor persisten en `lastError`/`errorMessage` como snapshot RFC 7807.
   807→- `StoryboardService`, `generate-image` y `generate-audio` son síncronos (latencias de segundos; ADR-014) con timeout de request `app.request_timeout_seconds`. Coherencia validada en arranque: `app.request_timeout_seconds` ≥ peor caso síncrono (timeout de proveedor × (`max_retries` + 1) + backoff acumulado) — regla del Anexo A.
   808→- El frontend sondea con `refetchIntervalMs` configurable (§5.2) solo mientras haya estados `*_pending` o jobs `pending/running`.
   809→- WebSockets: descartados en v1 (ver §1.8); el sondeo corto en single-user es suficiente y más simple de operar localmente.
   810→
   811→### 3.5 Subidas y almacenamiento
   812→
   813→- Validación de subidas (imagen base, imagen de referencia, música): `Content-Length` ≤ límite de config (`upload.*`) → si no, 413 ANTES de leer el cuerpo completo; mimetype ∈ whitelist → 415; verificación de magic bytes (formato real vs. extensión declarada) → 415 `UNSUPPORTED_MEDIA` con detalle.
   814→- El `storageKey` lo genera SIEMPRE el servidor (UUID + convención de directorios `uploads|outputs/projects/{projectId}/…`); el nombre de archivo del usuario solo se guarda como metadato en la BD, nunca como ruta (previene path traversal).
   815→- `StorageService` (puerto): `save(key, bytes)`, `open(key)`, `delete(key)`, `exists(key)`, `resolve_url(key)`; implementación `LocalFSStorage` con contención de rutas. Ruta a S3/MinIO futura: nueva implementación del puerto (ADR-002).

   818→
   819→## FASE 4 — Lógica de Inserción Extensible (JSON genérico validado)
   820→
   821→### 4.1 Objetivo y regla de extensibilidad
   822→
   823→El sistema recibe un **JSON genérico** para crear/editar `Reference` con atributos variables (`eyeColor`, `hairColor`, `outfit`, …) y debe: (1) aceptar claves nuevas sin cambios en backend ni en esquema relacional (regla del «Carro» del LISTÓN); (2) rechazar todo lo peligroso o fuera de límites con un error explícito (nunca descarte silencioso). La decisión de fondo (JSONB + JSON Schema vs EAV vs columnas) está justificada en §2.5; esta fase define el mecanismo de control completo.
   824→
   825→### 4.2 Esquema de validación y sus controles (todos los límites viven en config)
   826→
   827→`ReferenceValidator` (servicio de dominio, sin I/O) valida `attributes` contra el JSON Schema versionado `reference-attributes.schema.json` (Anexo C) **más** una pasada imperativa para las restricciones que JSON Schema no expresa de forma portable. Controles, cada uno con su clave de `config.yaml` (sección `reference.*`) y su código de error 422:
   828→
   829→| Control | Regla | Clave config | `code` del problema |
   830→|---|---|---|---|
   831→| C-01 Campos permitidos en el nivel superior | El modelo Pydantic de request solo acepta las claves del contrato (`type`, `name`, `description`, `libraryScope`, `projectId`, `level`, `attributes`); clave desconocida → rechazo | — (contrato Pydantic `extra="forbid"`) | `UNEXPECTED_FIELD` |
   832→| C-02 Tipos de valor aceptados | `string` \| `number` **finito** \| `boolean` \| `null` \| `array` de escalares \| `object` (anidado un nivel) | — (Anexo C) | `ATTRIBUTE_VALUE` |
   833→| C-03 Tamaño máximo del JSON de atributos | bytes del payload serializado | `attributes_max_json_bytes` (16384) | `ATTRIBUTE_LIMIT` |
   834→| C-04 Número máximo de claves | — | `attributes_max_fields` (32) | `ATTRIBUTE_LIMIT` |
   835→| C-05 Profundidad máxima | recorrido imperativo de profundidad (JSON Schema no tiene restricción nativa portable de profundidad) | `attributes_max_depth` (2) | `ATTRIBUTE_DEPTH` |
   836→| C-06 Longitud máxima de valores string | en **code points** Unicode (el total en bytes lo acota C-03) | `attributes_max_value_length` (200) | `ATTRIBUTE_VALUE` |
   837→| C-07 Tamaño máximo de arrays | — | `attributes_max_array_items` (8) | `ATTRIBUTE_VALUE` |
   838→| C-08 Nombres de clave seguros | regex `^[a-z][a-zA-Z0-9]{0,31}$` (sin `__`, sin `$`, sin puntos) **más** denylist de nombres peligrosos (`constructor`, `prototype`, `hasownproperty`, `tostring`, `valueof`) comparados en minúsculas; aplicado también al objeto anidado | `dangerous_key_denied` + Anexo C `propertyNames` (nivel superior y anidado) | `ATTRIBUTE_NAME` |
   839→| C-09 Claves sensibles prohibidas | denylist configurable, comparación en minúsculas; conjunto efectivo = **unión** de config y Anexo C (nunca intersección) | `sensitive_key_denied` | `SENSITIVE_KEY` |
   840→| C-10 Valores desconocidos pero válidos | **se aceptan** (extensibilidad): cualquier clave que pase C-02..C-09 entra en `attributes` | — | — (201/200) |
   841→| C-11 Versionado | sello `attributesSchemaVersion="v1"` en escritura; lectura tolera versiones anteriores | — | — |
   842→| C-12 Claves del objeto anidado | límite de claves del nivel 2 y mismas reglas C-08/C-09 recursivas | `attributes_max_nested_fields` (8) | `ATTRIBUTE_LIMIT` / `ATTRIBUTE_NAME` |
   843→| C-13 Claves duplicadas en el JSON crudo | rechazo explícito en el parser (object_pairs_hook) — nunca «última gana» en silencio | — (mecanismo del parser) | `VALIDATION_ERROR` |
   844→
   845→La pasada imperativa (C-03/C-05/C-06/C-07 y C-12/C-13) existe porque JSON Schema (draft-07, la más portable entre validadores Python `jsonschema`) no garantiza límites de bytes ni profundidad sin extensiones no estándar. Coste aceptado: ~40 líneas de código imperativo. Alternativa descartada: subir a draft 2020-12 con `$defs` + recursion — no cierra ni bytes ni profundidad y añade dependencia de versión de validador.

   847→### 4.3 Flujo end-to-end de inserción
   848→
   849→```
   850→Cliente → POST /api/v1/references
   851→  body: { "type": "character", "name": "Vera", "level": "advanced",
   852→          "libraryScope": "project", "projectId": "0f9d…",
   853→          "attributes": { "eyeColor": "brown", "hairColor": "castaño",
   854→                          "outfit": { "top": "white shirt", "bottom": "navy pants" } } }
   855→        │
   856→        ▼
   857→ReferencesController (presentation)
   858→  · Pydantic ReferenceCreateRequest (extra="forbid" ⇒ C-01)
   859→  · libraryScope=project exige projectId; global exige projectId null (INV-04)
   860→        │
   861→        ▼
   862→CreateReferenceUseCase (application)
   863→  · llama ReferenceValidator.validate(attributes)  [C-02..C-10 del §4.2]
   864→  · error ⇒ 422 con problema RFC 7807 (code específico + campo)   ← nunca descarte silencioso
   865→        │
   866→        ▼
   867→ReferenceFactory.create(...)  (domain)
   868→  · sella attributesSchemaVersion="v1"
   869→  · normaliza scope/projectId; defaults de level
   870→        │
   871→        ▼
   872→SqlAlchemyReferenceRepository.save (infrastructure)
   873→  · INSERT con attributes serializado JSON → columna JSONB (TEXT en SQLite)
   874→        │
   875→        ▼
   876→201 ReferenceResponse (echo de attributes validado)
   877→```
   878→
   879→### 4.4 Controles de seguridad (riesgo → control → prueba)
   880→
   881→| Riesgo | Control | Efecto |
   882→|---|---|---|
   883→| Path/prototype pollution (`__proto__`, `constructor`, `$type`) | C-08 (regex + denylist `dangerous_key_denied`) + `extra="forbid"` en nivel superior; además la serialización JSON de Python no arrastra prototipos — defensa en profundidad declarada | 422 `ATTRIBUTE_NAME` |
   884→| Exfiltración/almacenamiento de secretos en atributos | C-09 denylist de claves sensibles | 422 `SENSITIVE_KEY` |
   885→| DoS por payload gigante | límite de body global (`app.max_body_bytes`, 413) + C-03/C-04 | 413 / 422 `ATTRIBUTE_LIMIT` |
   886→| DoS por anidamiento profundo (parser) | C-05 profundidad | 422 `ATTRIBUTE_DEPTH` |
   887→| Inyección SQL | los valores van serializados a JSON en columna (sin concatenación); consultas parametrizadas en repos | n/a estructural |
   888→| Inyección en prompts | `PromptComposer` cita valores de atributos con comillas y límite de longitud (C-06); no interpola SQL/shell | n/a estructural |
   889→
   890→Declaración explícita: no se pretende detectar secretos por el **contenido** de valores (falsos positivos innecesarios en una herramienta local); el control es por **nombre de clave** y está configurado (C-09). Este es un alcance decidido, no una omisión.
   891→
   892→### 4.5 Versionado del esquema de atributos
   893→
   894→- Política de compatibilidad: **cambios aditivos** (nuevas claves permitidas, restricciones relajadas) → sube versión menor del JSON Schema (v1.1) sin migración de datos; los documentos sellados con versiones anteriores siguen siendo válidos de lectura.
   895→- **Cambios rompientes** (renombres, restricciones nuevas que invalidan datos existentes) → requieren revisión Alembic de datos (recorrido por `references`, revalidación, reporte de rechazos) y una decisión explícita de ADR. No se hacen «en silencio».
   896→- El sello `attributesSchemaVersion` permite al `ReferenceRenderer` (F5) decidir cómo mostrar datos viejos (p. ej., claves hoy desconocidas → sección «atributos adicionales»).
   897→
   898→### 4.6 Semántica de escritura aplicada a `attributes` (taxonomía §3.1.1 aplicada)
   899→
   900→| Caso en `PATCH /references/{id}` | Comportamiento |
   901→|---|---|
   902→| `attributes` ausente del payload | no se toca (valor previo intacto) |
   903→| `attributes: null` | 422 `VALIDATION_ERROR` — el campo es no-nullable (§2.3: «sin atributos» se representa con `{}`) |
   904→| `attributes: { … }` | **sustitución completa** del objeto (semántica declarada; para edición parcial de una clave, el cliente envía el objeto merged resultante; el use case re-valida al completo y **re-sella** `attributesSchemaVersion` con la versión vigente) |
   905→| clave nueva dentro (p. ej. `hairColor`) | aceptada si pasa C-02..C-10 (extensibilidad) |
   906→| clave con valor inválido (array de objetos) | 422 `ATTRIBUTE_VALUE` con ruta del campo |
   907→| `attributes` no es objeto (p. ej. `[]` o `"str"`) | 422 `VALIDATION_ERROR` con `field=attributes` (el DTO declara `attributes: dict[str, JsonValue]`) |
   908→| temporal / auth de proveedor / configuración / crítico en escritura | temporal, auth y configuración no aplican estructuralmente a una escritura local síncrona sin proveedor externo (declaración de imposibilidad, no omisión); un bug del validador → 500 `INTERNAL_ERROR` (taxonomía §3.1.1) |
   909→
   910→### 4.7 Frontend: registro de atributos conocidos (display config, no contrato)
   911→
   912→El `ReferenceRenderer` (F5 §5.4 — nombre lógico de la composición de las moléculas `ReferenceCard` + `AttributeRows`, §6.2) no conoce el universo de claves: mantiene un **registro de presentación** (fichero `src/config/reference-attributes.display.ts`) que mapea claves conocidas → etiqueta en español + tipo de visualización. Las claves no registradas se renderizan en la sección «Atributos adicionales». Promover `hairColor` de «adicional» a «conocido» = editar solo ese fichero de presentación (cambio frontend, opcional, sin backend).
   913→
   914→### 4.8 Ejemplo end-to-end de extensibilidad (regla del «Carro» del LISTÓN)
   915→
   916→Escenario del enunciado: mañana se añade el proveedor de video **ProviderX** y el atributo **`hairColor`** a personajes.
   917→
   918→**A) Nuevo proveedor ProviderX — flujo sin modificar el núcleo:**
   919→
   920→1. Se implementa `ProviderXVideoProvider` en `app/infrastructure/providers/providerx.py` cumpliendo el puerto `VideoProvider` (F6 §6.4: `generate`, `validate_config`, `capabilities → supported_durations, reference_image_limit`).
   921→2. Se registra en `providers.yaml` (Anexo B) con sus parámetros estáticos: `adapter`, `base_url`, `timeout_seconds`, `max_retries`, `backoff_base_seconds`, `max_concurrent`, `supported_durations`, `reference_image_limit`.
   922→3. El usuario crea su `ProviderConfig` por API/UI (`providerType=video`, `providerName=providerx`, apiKey cifrada).
   923→4. El proyecto elige `videoProvider="providerx"` (PATCH project).
   924→5. Flujo en ejecución **sin cambios en Scene, Project, use cases ni controllers**:
   925→
   926→```
   927→SceneController(POST /scenes/{id}/generate-video)
   928→  → GenerateSceneVideoUseCase
   929→      → VideoProviderFactory.create("providerx")   ← resuelve registry + ProviderConfig
   930→      → ProviderXVideoProvider.generate(VideoGenerationRequest)
   931→  → StorageService.save(clip) → SceneRepository.update(path, status)
   932→```
   933→
   934→Comparación con la alternativa descartada: con `if provider == "veo": … elif …` en el use case, cada proveedor nuevo exige editar y re-testear el núcleo — exactamente lo que el LISTÓN prohíbe.
   935→
   936→**B) Nuevo atributo `hairColor` — flujo sin modificar núcleo ni esquema:**
   937→
   938→1. El usuario envía `POST /api/v1/references` con `attributes: {"hairColor": "castaño"}`.
   939→2. `ReferenceValidator`: la clave pasa C-08 (regex) y no está en C-09 → **aceptada** (C-10).
   940→3. Se persiste en `attributes` (JSONB) con sello v1 — sin ALTER TABLE, sin tocar entidades, repos ni use cases.
   941→4. `PromptComposer` incluye dinámicamente los atributos del nivel `advanced`/`cinematic` al construir `promptEn` de las escenas donde la referencia está asignada como `subject` (recorre `attributes` como diccionario, no hay lista fija de campos en el código).
   942→5. `ReferenceRenderer` la muestra (en «adicionales» hasta que se registre su etiqueta — §4.7).
   943→
   944→**C) Distinción explícita** (exigida por el LISTÓN): añadir un atributo o un proveedor compatible = **datos/variantes compatibles** (cerrojos en config y registro; sin tocar núcleo). Añadir **comportamiento de negocio nuevo** (p. ej., un tipo de asset distinto como video de transición, o un paso nuevo en el pipeline) sí puede requerir código, pruebas y despliegue — se declara sin ambigüedad: la extensibilidad garantizada es la de los ejes de variabilidad aislados por puertos (proveedores, storage, ensamblaje) y la de datos dinámicos (atributos JSONB), no la de reescribir la semántica del pipeline gratis.

   948→## FASE 5 — Estrategia de Renderizado Dinámico y Listas
   949→
   950→### 5.1 Principios de renderizado
   951→
   952→1. **Clave = UUID, nunca el índice.** Toda lista (`scenes`, `references`, `visualStyles`, `voices`, `jobs`, `providerConfigs`) renderiza `key={item.id}`. El reordenamiento (`PUT /scenes/order`) y el borrado intermedio no desmontan tarjetas equivocadas (React reconcilia por clave; con índice reutiliza nodos con datos cruzados — defecto clásico que el LISTÓN prohíbe).
   953→2. **Iteración dinámica sobre los datos, no sobre un molde fijo**: los componentes no enumeran campos de `Scene`/`Reference` «a mano»: renderizan a partir de los DTOs del API y del registro de presentación (§4.7). Campos nuevos del DTO aparecen sin tocar componentes (los DTOs TypeScript se generan/escriben espejo del contrato Pydantic de F3).
   954→3. **Los límites de negocio llegan del backend**: `useRuntimeConfig()` (TanStack Query sobre `GET /api/v1/config`) alimenta `DurationSlider` (min/default/max), límites de subida y whitelists. El frontend **no duplica** rangos de negocio (cero hardcoding, §1.9).
   955→4. Las constantes UI que sí viven en el frontend (`src/config/app.config.ts`) son solo de rendimiento, con valor y motivo declarados aquí: umbral de virtualización (50 — por encima, el DOM crece linealmente), alturas estimadas (px — cálculo del virtualizador), `staleTimeMs` (15 000 — evita refetch al alternar pestañas del workspace), `retryCount` (2 — red local; más reintentos solo molestan), `refetchIntervalMs` (2 000 — sondeo de `*_pending`/jobs). El fichero repite estos motivos en comentarios.
   956→
   957→### 5.2 Estructura de queries (TanStack Query) e invalidación
   958→
   959→Claves canónicas (siempre con el identificador estable, nunca índices):
   960→
   961→```
   962→['runtime-config']
   963→['projects', {filters}]                          → useInfiniteQuery (cursor = pageParam)
   964→['project', projectId]
   965→['scenes', projectId, {filters}]                → useInfiniteQuery (sortBy=order)
   966→['scene', sceneId]
   967→['references', {scope, projectId, filters}]      → useInfiniteQuery
   968→['visual-styles', {origin}]                      → useInfiniteQuery
   969→['provider-configs', {providerType}]             → useInfiniteQuery
   970→['tts-voices', {provider}]                       → useInfiniteQuery
   971→['assemblies', projectId]                         → useInfiniteQuery
   972→['assembly', jobId]
   973→```
   974→
   975→El cursor nunca forma parte de la clave (es `pageParam` interno de `useInfiniteQuery`); **toda** colección marcada **P** en §3.2 se consume como lista infinita — ninguna lista de entidad se trunca a la primera página.
   976→
   977→Matriz de invalidación (mutación → qué se invalida):
   978→
   979→| Mutación | Invalida |
   980→|---|---|
   981→| `POST /projects` | `['projects']` |
   982→| `POST /projects/{id}/storyboard` | `['project', id]`, `['scenes', id]` (refetch completo: reemplaza escenas) |
   983→| `PATCH /scenes/{id}` | `['scene', id]` + entrada correspondiente en el caché de `['scenes', projectId]` (actualización de caché por matcher de `id`) |
   984→| `PUT /scenes/order` | `['scenes', projectId]` |
   985→| `generate-image`/`image`/`delete asset` | `['scene', id]` |
   986→| `generate-video` (202) | `['scene', id]` con `refetchInterval` activo mientras `status=video_pending` |
   987→| `generate-audio` | `['scene', id]` |
   988→| `POST /projects/{id}/assemble` | `['assemblies', id]` + sondeo del job creado |
   989→| `PATCH /projects/{id}` | `['project', id]` + `['projects']` |
   990→| `DELETE /projects/{id}` | `['projects']` + purga de `['project', id]`, `['scenes', id]`, `['assemblies', id]` |
   991→| `POST /projects/{id}/music` / `DELETE …/music` | `['project', id]` |
   992→| `POST /projects/{id}/audio-qa` | `['assemblies', id]` + sondeo del job creado |
   993→| `DELETE /scenes/{id}` | `['scenes', projectId]` + purga de `['scene', id]` + `['project', id]` (estado/`sceneCount`) |
   994→| `PUT /scenes/{id}/references` | `['scene', id]` (confirmación post-optimista) |
   995→| imágenes de referencia (`POST`/`DELETE`/`PATCH /references/{id}/images…`) | `['references', …]` + `['reference', id]` |
   996→| CRUD referencias/estilos/configs | la lista y el detalle correspondientes |
   997→
   998→Regla general: toda mutación 2xx invalida el detalle de su recurso y su lista canónica; la matriz enumera los casos no triviales (matchers por `id`, purgas y sondeos).
   999→
  1000→Sondeo: `refetchIntervalMs` de `app.config.ts` solo mientras existan estados pendientes (la condición se evalúa con los datos en caché; sin estados pendientes el sondeo se apaga — sin temporizadores zombis).
  1001→
  1002→### 5.3 Virtualización de listas grandes
  1003→
  1004→- `StoryboardList` y `ReferenceLibrary` usan `@tanstack/react-virtual` cuando `items.length > virtualization.threshold` (50). Por debajo del umbral se renderiza la lista normal — el virtualizador no aporta con decenas de nodos y complica la accesibilidad por teclado (declaración de coste). El umbral es constante de rendimiento UI documentada (§5.1 p.4), no un límite de negocio.
  1005→- Esquema (ilustrativo del mecanismo, no código de producción):
  1006→
  1007→```tsx
  1008→const parentRef = useRef<HTMLDivElement>(null);
  1009→const { data } = useInfiniteScenes(projectId);          // cursor infinito
  1010→const rows = useMemo(() => data.pages.flatMap(p => p.items), [data]);
  1011→const virtualizer = useVirtualizer({
  1012→  count: rows.length,
  1013→  getScrollElement: () => parentRef.current,
  1014→  estimateSize: () => APP_CONFIG.virtualization.sceneRowEstimatePx,
  1015→  overscan: APP_CONFIG.virtualization.overscan,
  1016→  getItemKey: (index) => rows[index].id,               // clave estable UUID, no index
  1017→});
  1018→```
  1019→
  1020→- `useVirtualizer` con `getItemKey` por `id` mantiene la identidad de los nodos al hacer scroll y al invalidar páginas (React reutiliza el componente correcto).
  1021→- «Cargar más» infinito: el sentinel de `useInfiniteQuery` (`fetchNextPage`) se monta como fila virtual final con una **clave reservada fuera del dominio** (`'__load-more__'`); `getItemKey` la devuelve para el índice final (`count = items + 1`) y el cursor del API alimenta la siguiente página.
  1022→- Límites prácticos declarados: DOM simultáneo ≈ viewport/altura + overscan (decenas de nodos); memoria del caché acumulada de páginas cargadas (lineal en lo ya cargado — si el usuario recorre 10.000 escenas, el caché crece; se declara y se mitiga con `gcTime` que descarta páginas lejanas si el componente se desmonta); ancho de banda acotado por `pagination.max_page_size` del backend.
  1023→
  1024→### 5.4 Manejo de campos ausentes, nulos y desconocidos (tabla por componente)
  1025→
  1026→Taxonomía §3.1.1 aplicada al render (ausente ≠ null ≠ desconocido):
  1027→
  1028→| Componente | Campo | Ausente / null | Valor desconocido |
  1029→|---|---|---|---|
  1030→| `SceneCard` | `imageBasePath`/`videoClipPath`/`audioPath` | `null` → chip de estado «pendiente» (semántica §2.3) — nunca se inventa placeholder de imagen | — |
  1031→| `SceneCard` | `lastError` | `null` → sin badge de error | `code` del problema no mapeado → badge genérico «Error no clasificado» con `traceId` visible (no se oculta) |
  1032→| `ReferenceCard` | `attributes.eyeColor` | clave ausente → la fila no se renderiza (ausencia ≠ dato) | clave no registrada → sección «Atributos adicionales» |
  1033→| `ReferenceCard` | `attributes.eyeColor = null` | valor null explícito → fila con «—» y tooltip «Valor nulo registrado» (null ≠ ausente, se muestra) | ídem |
  1034→| `ReferenceCard` | `attributes.someKey` de tipo objeto | se renderizan sus sub-pares (profundidad ≤ 2 validada en backend) | ídem |
  1035→| `StylePicker` | `description` | `null` → sin subtítulo (ausencia documentada) | — |
  1036→| `ErrorNotice` | `hints[]` | ausente → solo detalle | ídem |
  1037→
  1038→Regla general: **ausente ⇒ omitir la fila; null ⇒ mostrar «—»; desconocido ⇒ mostrar con marcado claro**. Ninguna conversión silenciosa a valores por defecto visuales (LISTÓN: no ocultar la diferencia).

  1056→### 5.6 Actualizaciones optimistas acotadas
  1057→
  1058→- Se aplican solo a `PATCH /scenes/{id}` (duración, prompt, textos) y `PUT /scenes/references` — operaciones de conflicto bajo con un único usuario local.
  1059→- Mecanismo: actualizar el caché de `['scene', id]`/entrada de lista de inmediato, rollback automático del previous snapshot si la mutación falla, y `ErrorNotice` con el problema real. El rollback evita el estado fantasma «parece guardado pero no lo está» (LISTÓN: no ocultar errores).
  1060→- NO se aplican optimistas a generación de assets ni ensamblaje (operaciones largas con estados asíncronos: sería fingir un estado inexistente).
  1061→
  1062→### 5.7 Rendimiento y límites declarados
  1063→
  1064→- `React.memo` en `SceneCard` y `ReferenceCard` con comparador explícito (`id`, `status`, `durationSeconds`, paths de assets, `level`, `name`, `attributes` por igualdad superficial — suficiente porque PATCH sustituye `attributes` por completo, §4.6; dependencia declarada): problema que resuelve — al parchear una escena, no re-renderizar las otras 199 tarjetas del storyboard. Coste — mantener el comparador al añadir props visibles. Alternativa descartada — re-render completo.
  1065→- Re-renders inevitables declarados: cambio de filtro/sort reconstruye la lista (invalidación de query) — acotado por página.
  1066→- Ningún `useEffect` con fetch manual en organismos (condiciones de carrera); toda lectura pasa por TanStack Query (§1.6).
  1067→- Declaración de límite real: la virtualización optimiza el DOM, no el tamaño del caché acumulado; con >10.000 escenas cargadas en una sesión, el caché de cliente ocupa memoria proporcional (documentado; mitigación `gcTime`).

  1208→class VideoProvider(Protocol):

  1258→    async def save(self, key: str, content: bytes) -> None: ...
  1259→    async def open(self, key: str) -> bytes: ...
  1260→    async def delete(self, key: str) -> None: ...
  1261→    async def exists(self, key: str) -> bool: ...

  1505→  "additionalProperties": {
  1506→    "oneOf": [
  1507→      { "type": ["string", "number", "boolean", "null"] },
  1508→      { "type": "array", "maxItems": 8,
  1509→        "items": { "type": ["string", "number", "boolean", "null"] } },
  1510→      { "type": "object",
  1511→        "maxProperties": 8,
  1512→        "propertyNames": { "$ref": "#/definitions/safeKey" },
  1513→        "additionalProperties": { "type": ["string", "number", "boolean", "null"] } }
  1514→    ]
  1515→  },
  1516→  "definitions": {
  1517→    "safeKey": {
  1518→      "pattern": "^[a-z][a-zA-Z0-9]{0,31}$",
  1519→      "not": { "enum": ["apikey", "password", "secret", "token", "authorization", "privatekey",
  1520→                        "constructor", "prototype", "hasownproperty", "tostring", "valueof"] }
  1521→    }
  1522→  }
  1523→}
  1524→```
  1525→
  1526→Los límites dimensionales que JSON Schema no expresa de forma portable (bytes totales, profundidad total, longitud de cada string) los impone la pasada imperativa C-03/C-05/C-06 con valores de `config.yaml` (§4.2). El `maxProperties`/`maxItems` del schema se sincroniza con config en arranque (el validador toma siempre el mínimo de ambos — los valores del Anexo A/C coinciden deliberadamente 32/8, incluido el anidado 8 = `reference.attributes_max_nested_fields`). El conjunto de claves prohibidas efectivo es la **unión** de `sensitive_key_denied` y `dangerous_key_denied` (Anexo A) con el `enum` del schema, comparado en minúsculas (nunca la intersección); la comparación normalizada la ejecuta el validador. La protección real contra contaminación de prototipos es además estructural: la serialización JSON de Python no arrastra prototipos (defensa en profundidad declarada en §4.4).
